# 审查意见处理

每条审查意见先当成待核对的假设。读取需求、当前补丁、调用合同和可用运行证据，再判断是否修改。
上游的故障报告和用户提出的新功能都是可调查的依据；上游机器的耗时或成功率不自动适用于本仓。

- **已确认**：说明现象、根因和最小修复，补行为测试与适用的真实只读验证。
- **证据不足/未验证**：列出缺少的页面、日志、权限或复现条件；不猜 selector、不补默认值、不加盲目重试来伪装修好。
- **重复/已过时/不适用**：指出当前代码或范围依据，不为凑回应改代码。

逐条记录“结论、证据、动作、验证、提交”。只有真实读到的数据才能称采集成功；fixture 只验证对应机制。
检查行内线程及回复、是否已解决/过时，以及顶层评论；只读扁平评论列表不足以判定线程已经处理。
修复后检查远端 diff、提交和 CI，不把机器人摘要当成已推送的代码。需要外部审查机器人采取行动时，必须先有用户或已调用工作流的明确授权。
未解决的实测条件继续写在 PR，不能把历史结果移到新提交名下。最后更新 PR 正文的验证状态。
